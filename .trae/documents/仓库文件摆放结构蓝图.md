1. **根目录拥挤**：7 份 2.9 MB 程序副本（根 txt、根 html、`index.html`、`work/` 两份、`pre/target/` 两份）+ 4 个目录平铺，首屏看不到项目全貌。
2. **`tool/` 是 60+ 个脚本平铺**：构建、闸门、报告、verify-* 真机验证、`*.legacy` 遗留混在一起（用户已明确：待会再讨论，本次不动）。
3. **没有面向使用者的辅助程序**：README 让用户手动跑 `md5sum`/`wc` 校验指纹、手动 `node tool/serve.mjs` 起服务，与"下载一个文件就能用"的产品特点不符。

用户已定的边界：

## 设计原则（契合程序特点）

- **单文件交付**：成品就是一个 HTML，使用者不需要 clone、不需要 npm。任何结构改动不能让"下载即用"变复杂。
- **src/ 是唯一编辑真源，根 txt 是构建产物**：目录规划必须保持 `src/ → build → 根 txt → deploy → 副本` 这条链的路径不动（`tool/patch.mjs` 是路径唯一真源，41 个脚本引用它）。
- **字节契约不可破**：六份副本一致是 `selfcheck` 硬闸门，本方案不碰。
- **GitHub Pages 依赖根 `index.html`**：根目录必须保留它。

## 结构蓝图

```
beifeng-reader/
├── README.md · LICENSE · .gitignore · .gitattributes   # 项目脸面（现状）
├── index.html                    # Pages 入口（副本之一，不动）
├── 北风V0.0.1-alpha.html          # 成品，用户直接下载这份（不动）
├── 北风V0.0.1-alpha.txt           # 构建产物/编辑母本（不动）
├── work/ · pre/target/           # 契约副本（不动）
│
├── src/                          # 唯一编辑源（现状，不动）
├── tool/                         # 构建+检查脚本（分组待讨论，本次不动）
│   ├── …现有平铺脚本…
│   └── tests/
│
├── docs/                         # ARCHITECTURE / DESIGN-NOTES（现状）
├── screenshots/                  # README 用图（现状）
│
└── scripts/                      # ★ 新增：用户向辅助程序（本次唯一动手项）
    ├── verify.sh                 # 一条命令指纹校验（md5 + 行数/字节数，替代 README 手动命令）
    └── start.sh                  # 一条命令起本地服务并提示地址（包装 tool/serve.mjs）
```

要点：
- **根目录三类东西**：交付物（html/txt/LICENSE/README）、入口（index.html）、目录（src/tool/docs/screenshots/scripts/work/pre）。副本保持原位，根目录不再新增大文件。
- **`scripts/` 与 `tool/` 分工**：`scripts/` = 使用者双击/一条命令能跑的；`tool/` = 维护者跑的只读检查。边界写进两个 README，避免以后又混回去。
- **辅助程序为什么契合特点**：
  - `verify.sh` —— README §"怎么确认你拿到的是完整的程序" 现在要用户手敲两条命令、人工比对 md5；脚本直接给出 ✓/✗ 结论，符合"零知识也能验货"。
  - `start.sh` —— README 已说明 `file://` 下 IndexedDB 被禁、数据功能不完整；脚本一条命令起服务并打印地址，把"推荐用法"降到零门槛。
  - 两者都只包装现有脚本（`tool/serve.mjs`、`md5sum`/`wc`），不引入任何依赖，不进成品单文件。
