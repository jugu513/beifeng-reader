# 设计取舍

这里记的是"为什么",不是"怎么做"。代码会变，这些判断短期内不会。

## 本地优先，不做云

书、进度、划线、笔记、设置全部留在设备本地。程序里没有服务器地址，也没有把正文发出去的代码路径。

这不是偷懒，是承诺。一个阅读器一旦把正文交给服务器，就得处理账号、隐私、费用和服务关停。本地文件没有这些风险——十年后它还能打开。

代价是换设备要手动导出导入，没有云同步的便利。这个代价是刻意选的。

## 单个文件

所有 HTML、CSS、JS 塞进一个文件。体积 2.9 MB，没有运行时依赖。

文件是最耐久的载体：能拷进 U 盘、能通过任何方式发送、十年后双击就能用。它不需要 npm，不会遇到依赖失效或 CDN 下线。

代价是文件不好读、构建要额外写工具。所以才有 `src/` 的拆分和整套闸门——用工程手段补单文件的短板，而不是放弃单文件。

## 数据分三级存储

浏览器给了三种本地存储，各有长短，程序按数据类型分配：

- **localStorage**：同步读、快的那些——书签、进度、设置、元数据。这些必须在页面加载瞬间就能拿到，不能等异步。
- **IndexedDB**：大块、可重建的内容——书的正文字、摘要。
- **OPFS**：更大的文件句柄。

承重键（书签/划线/进度这类）的主存必须留在同步的 localStorage。曾考虑过全迁到异步后端，但那会让书架在打开瞬间读空，所以否掉了。可选的后端分配只对"大体积、可重建"的内容开放。

## 降档，不升档

对外能力（在线语音、AI 端点）默认走保守形态，探测到支持才升档。理由很简单：升错档功能直接失败，降错档只是质量差一点。

自动探测和手动锁档要同时给——程序探测出一个默认档，设置里也能自己锁死。探测不过时如实告诉用户现在走的是哪条路，不静默。

## 界面 = 四件事

"界面优化"在这个项目里不只是好看，是四件事一起：

1. 视觉质感
2. 交互
3. 微交互
4. 信息密度

而且覆盖所有页面，包括设置，不只是阅读器。一个设置页挤成一团，阅读器再漂亮也没用。

## 明确不做的

这些是反复调查后裁定不动的，不是还没做：

- **拆大文件**。`129.js` 有三千多行，但 AST 分析证明它不是巨型函数，是顺序切片的层文件，内部已经拆好了子函数。强拆只会破坏字节一致契约。
- **继续加功能**。功能密度已经很高，再堆只增加复杂度，不增加价值。
- **大规模清注释**。注释绝大多数是高质量的"为什么"注释，没有可安全批量删除的空间。
- **第二套构建脚本**。`build.mjs` 是唯一的生成入口，再来一条写入路径就破坏了单一真源。
- **幂等去重、固定右留白、通知红点、书架列数**这类细节。多轮评估过，维持现状。

## 不静默

写失败不许报成功。删除要如实说明删了哪几层、各多少条。文案承诺了几件事就分别报告几件事——"已保存但套色失败"和"没存进书库（空间不足）"是两种不同的结果，不能混成一句"操作失败"。

破坏性操作必须有确认和回响，区分失败 / 部分成功 / 成功。

## 印章作为品牌

品牌色是朱砂——印章和朱批的颜色。标签页图标是一枚朱砂方印配三道风纹，呼应"北风"。这个意象贯穿在书封的首字印章和主题系统里。
